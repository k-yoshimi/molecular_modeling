# CSP の緩和に機械学習ポテンシャル（OrbMol-v2）を使えるようにする：設計書

- 日付: 2026-11-07
- 前提: `docs/superpowers/specs/2026-10-30-crystal-structure-prediction-design.md`（CSP 本体の設計。PR #3 で main に統合済み）
- 根拠資料:
  - 文献調査メモ（2026-11-05）。候補モデルの対応元素、学習データ、分子結晶ベンチマーク、ライセンスを比べた。
  - 手元の比較試験（2026-11-06、Apple M2・8 コア・24 GB）。結果は 2 節。

## 1. 意図と背景

CSP の緩和と順位付けは、今は GFN2-xTB（tblite）に固定されている。利用者の希望は、**Se を含む一般の有機分子結晶**で、xTB より信頼できる順位を得ること。同じ1時間でより多くの候補を緩和できれば、なお良い。そのために機械学習ポテンシャル（MLIP）を使えるようにしたい。

候補の絞り込み（文献調査）:
- MACE-OFF、SO3LR、ANI-2x は Se を扱えないので外した。
- 無機材料向けの汎用モデル（MACE-MP-0 など）は、分子結晶の格子エネルギーの誤差が大きいので外した。
- UMA（Meta）の分子結晶タスクは公開実績が最も厚い。ただし次の理由で後回しにした（7 節）。
  - 学習データ OMC25 に Se がない。
  - 重みの取得に Hugging Face での利用申請が要る。
  - Apple GPU に対応していない。
- AIMNet2 と OrbMol-v2 は、手元で試した。

## 2. 手元の比較試験の結果（判断の根拠）

対象は3つの実験結晶（COD）:
- ナフタレン（2311090）
- 3-セレノシアナトピリジン（2009756、Se を含む）
- ジフェニルジセレニド（4102296、Se を含む）

それぞれ実験構造と、PyXtal のランダム候補（12, 12, 6 個）を、FIRE + FrechetCellFilter で 300 ステップまでセル込みで緩和した。並列はせず、1 ジョブを 8 スレッドで流した。

| 方法 | 候補1個あたりの平均時間 | 実験構造が全候補より低いか | 問題 |
|---|---|---|---|
| GFN2-xTB（現行） | 91〜138 秒 | ナフタレンでは候補 1 個が 20 kJ/mol 低い | ジフェニルジセレニドの実験構造で SCF が収束せず失敗 |
| OrbMol-v2 | 48〜77 秒 | 3 系とも実験構造が最も低い（39〜89 kJ/mol の差） | なし |
| AIMNet2 | 9〜16 秒 | 2 系で全候補が実験構造より低い（最大 72 kJ/mol） | 結晶の順位付けに使えない |

- 結合の切断・生成、分子数の変化は、どの方法でも 0 件だった（計 30 候補）。
- OrbMol-v2 と xTB の候補順位の相関（スピアマン）は 0.75〜1.0 だった。
- 分子向けの orb-v3-conservative-omol は、OrbMol-v2 とほぼ同じ結果だった（順位相関 0.94〜1.0）。

**この試験の限界**:
- 系と候補が少ない。
- 候補は PyXtal の普通の密度のもので、本パイプラインの詰まった候補ではない。
- DFT との照合をしていない。
- 速度は「1 ジョブ 8 スレッド」での値である。本パイプラインの「1 ワーカー 1 スレッド × 8 並列」での値ではない。

## 3. ゴール・非ゴール・アンチゴール

### ゴール
- 設定 `relax_method` で、緩和の計算方法を `"GFN2-xTB"`（既定）と `"OrbMol-v2"` から選べる。
- `"OrbMol-v2"` を選んでも、既存の流れ（時間予算、壊れた候補の除外、staging と公開、ロック、検証、`error:` 1 行のエラー）がそのまま働く。
- 計算方法を後から足せる形にする（UMA などを、計算器の作り方を1つ足すだけで加えられる）。
- OrbMol-v2 の依存（PyTorch 等）は、入れたい人だけが入れる。xTB だけを使う人のインストールは重くしない。

### 非ゴール
- UMA、AIMNet2、MACE 系の組み込み（7 節）。
- GPU や Apple MPS での実行。CPU のみとする。
- 2段構成（xTB で粗く緩和してから MLIP で仕上げる）。必要かどうかは 6 節の計測で決め、必要なら別の変更とする。
- DFT による再順位付け。
- 電荷を持つ分子や開殻分子。中性・一重項（charge 0, spin 1）に固定する。

### アンチゴール
- 既定（xTB）の利用者の結果や速度が変わる。
- `"OrbMol-v2"` を選んだのに、黙って xTB で計算される（またはその逆）。
- ラウンドごとにモデルを読み直して、時間予算の大半をモデルの読み込みに使う。
- 重みのダウンロードに失敗したことが、緩和の途中で全候補の `failed` として現れる（最初に 1 行のエラーで止まるべき）。
- 計算方法の違う結果が、同じ出力ディレクトリの中で混ざる、または区別できない（`candidates.csv` だけを取り出したときも含む）。
- 親プロセスで PyTorch を初期化したあとにワーカーを fork して、Linux でワーカーが固まる。

## 4. 制約

- Python 3.11 以上（既存どおり）。macOS（Apple Silicon）と Linux で動くこと。
- OrbMol-v2 は `orb-models` パッケージ（Apache 2.0）を使う。2026-11-06 の試験では v0.7.0 だった。依存として PyTorch と NVIDIA Warp（CPU でも使われる）が入り、環境は約 1 GB 増える。
- 重みは初回にネットから取得し、`~/.cache/cached_path` に保存される。オフラインの計算機では、事前に取得しておく必要がある。
- 対応元素は既存の CSP と同じ（H, C, N, O, F, S, Cl, Se, Br, I）。OrbMol-v2 の学習データ（OMol25）はこれらをすべて含む。
- エネルギーの絶対値は方法ごとに基準が違う。比べてよいのは同じ方法の中での相対エネルギーだけである。

## 5. 決めたこと

### 5.1 設定と CLI
- `CSPConfig` に `relax_method: str = "GFN2-xTB"` を足す。
  - 入力ファイル（`load_csp_config`）で許す値は、`"GFN2-xTB"`, `"GFN1-xTB"`, `"OrbMol-v2"`。
  - 不正な値は、既存の値検査と同じく `ValueError` にし、`error:` 1 行で報告する。
  - テスト用の `EMT` 系は、入力ファイルからは選べない。
- `run_csp(cfg, method: str | None = None)` とする。
  - `method` を省略したら `cfg.relax_method` を使う。
  - `method` を指定したら、それで上書きする。テストで `EMT` 系を渡す道はこれで残す。
  - `relax_many` と `_relax_with_budget` も、方法名を引数で受け取る今の形を保つ。
- CLI に `--relax-method {GFN2-xTB,GFN1-xTB,OrbMol-v2}` を足す。
  - 指定すれば設定ファイルの値より優先する【Claude の判断】。
  - 上書きしたことは `run.log` に書く。
- 既定値は `"GFN2-xTB"` のままにする【Claude の判断。利用者にはまだ確認していない】。理由は二つ。
  - 既存の利用者に影響を出さない。
  - OrbMol-v2 の依存（約 1 GB）を全員に強いない。
- 6 節の計測で OrbMol-v2 が良くても、**コードの既定値は変えない**。ガイドと `input/csp.toml` のコメントで、Se を含む分子などに OrbMol-v2 を勧める【Claude の判断】。

### 5.2 インストール
- `pyproject.toml` に新しい extra を足す。
  - `csp-ml = ["molecular_modeling[csp]", "orb-models>=0.7,<0.8"]`。`csp` の依存も含めるので、`pip install -e ".[csp-ml]"` の1回で揃う。
  - 依存はすべて Apache 2.0（2026-11-07 に確認）: orb-models 0.7.0、warp-lang 1.19.0、torch、cached-path。
  - extra として任意に入れるものなので、本体の LGPL-2.1-or-later と衝突しない。
- `check_dependencies(method)` は、方法ごとに必要なものを確かめる。
  - `OrbMol-v2` では、共通の `pyxtal`, `pymatgen`, `spglib` と、`orb_models` と `torch` の**存在だけ**を `importlib.util.find_spec` で確かめる。親プロセスで torch や warp を import しないためである（5.3 節）。`tblite` は要求しない。
  - `orb_models.forcefield.pretrained.orbmol_v2` と `ORBCalculator` が import できるか（属性の確認）は、5.4 節の動作確認の子プロセスで行う。
  - 足りないときの案内は `pip install -e ".[csp-ml]"` にする。`require` の案内文は、呼ぶ側から渡せるようにする。

### 5.3 プロセス、プール、モデルの読み込み
- **ワーカーは常に `spawn` で起動する。** `ProcessPoolExecutor(mp_context=multiprocessing.get_context("spawn"))` とする。
  - macOS では今も spawn なので、変わるのは Linux だけである。
  - PyTorch と Warp を初期化したプロセスを fork する危険を、方法によらずなくす。
- **親プロセスでは MLIP のモデルを読み込まず、PyTorch も import しない。** 依存チェックはパッケージの存在の確認だけにする（5.2 節）。import と動作の確認は 5.4 節のとおり子プロセスで行う。
- **プールは、1 回の緩和段階（`_relax_with_budget` の呼び出し）の中で作り、抜けるときに必ず閉じる（`with` か `try/finally`）。** モジュール変数には置かない。
- **プールを新しく作るときは、必ず 1 つのヘルパーを通す。** ヘルパーは、プールを作り、準備ジョブ（5.6 節）を流し、準備時間を `run.log` に書く。最初のプールにも、ワーカーが落ちたあとに作り直すプールにも、同じヘルパーを使う。
  - すべてのラウンドで同じプールを使い回す。
  - `relax_many` は、外から渡されたプールを使える形にする。プールを渡されないときは今と同じく自分で作って閉じるので、既存の呼び方とテストは変わらない。
- **ワーカーが落ちたときの扱いは、今の仕組みを保つ。** 結果を失ったジョブは、1 個ずつ別の単独ワーカーで流し直して、落とした候補だけを `failed` にする。
  - 壊れたプールはその場で閉じ、次のラウンドの前に新しく作る。
  - 作り直したプールでは、モデルの読み込みがもう一度起きる。これは許す。
- **計算器はワーカーの中でキャッシュする。** ワーカー内のモジュール変数に、方法名をキーとして計算器を持たせる。モデルの読み込みはワーカーごとに 1 回で済む。
  - モデルの読み込みは、プールの `initializer`（ワーカーの起動時に 1 回だけ走る関数）で行う。準備ジョブは「全ワーカーが起動し終えたこと」を待つためのもので、先に起動したワーカーが準備ジョブをまとめて片付けても、読み込みは全ワーカーで済んでいる。
  - ワーカーの初期化で、`OMP_NUM_THREADS=1` と `torch.set_num_threads(1)`（torch がある場合）を設定する。
- OrbMol-v2 の計算器は、`orbmol_v2(device="cpu")` と `ORBCalculator(model, adapter, device="cpu")` で作る。
  - 緩和の前に `atoms.info["charge"] = 0`, `atoms.info["spin"] = 1` を入れる（OrbMol は両方の指定を必須とする）。

### 5.4 失敗を早く知らせる
- 実行の最初（出力ディレクトリに触る前、既存の依存チェックのすぐ後）に、**動作確認**をする。
  - spawn した子プロセスを 1 つだけ使う。
  - 子プロセスでは、計算器を作り（重みの取得を含む）、小さな分子（水 1 分子を周期セルに入れたもの）でエネルギー・力・応力を 1 回計算する。
  - 子プロセスは確認が済んだら終わる。親にモデルは残らない。
- 動作確認の子プロセスには 10 分のタイムアウトを設ける【Claude の判断】。重みの初回ダウンロードを含めても、普通の回線なら十分に収まる長さである。
  - 超えたら子プロセスを止め、下の `RelaxBackendError` で知らせる。
- 動作確認が失敗したら、新しい例外 `RelaxBackendError`（`RuntimeError` の派生）を投げる。
  - `cli.py` の `EXPECTED_ERRORS` にはこの型だけを足す。汎用の `RuntimeError` や `OSError` は足さない（本物のバグのトレースバックを隠さないため）。
  - メッセージは 1 行で、次を含める。
    - 方法名
    - 元の例外の型と要約
    - 重みのキャッシュ場所
    - オフラインの計算機での対処: ネットにつながる計算機で `python -c "from orb_models.forcefield import pretrained; pretrained.orbmol_v2(device='cpu')"` を実行し、`~/.cache/cached_path`（または `CACHED_PATH_CACHE_ROOT` が指す場所）をディレクトリごと持ってくる。
- xTB の方法では、動作確認をしない【Claude の判断】。今まで要らなかったので、xTB の利用者の起動を遅くしない。

### 5.5 記録
- `run.log` の最初に、どの方法でも同じ書式で次を書く。
  - `relax_method`
  - その値の出どころ。次の 4 種類のどれかを書く。
    - `default`: 設定ファイルに書かれていない
    - `config`: 設定ファイルに書かれている
    - `cli`: `--relax-method` で上書きした
    - `argument`: Python から `run_csp(..., method=...)` で上書きした
  - 出どころは `CSPConfig` の入力でない項目（`config_warnings` と同じ扱い）として持たせる。
    - ローダーは `default` か `config` を入れる。
    - CLI は `--relax-method` を受けたら `cfg.relax_method` を書き換え、出どころを `cli` にする。
    - `run_csp` は `method` 引数を受けたら `argument` にする。
  - 計算器のパッケージとバージョン（`tblite` または `orb-models`）
  - OrbMol-v2 では、重みのファイル名とキャッシュ場所
- 動作確認は `run.log` を開く前に行う。そのため結果は保持しておき、既存の `config_warnings` と同じ流れで、ログを開いた直後に書く。
- `candidates.csv` の**末尾**に `relax_method` 列を足す【Claude の判断。レビューの指摘を受けて変更】。値は、その実行で実際に使った方法名（上書き後の値）とする。
  - CSV だけを取り出して比べたときにも、方法の違いが分かるようにするため。
  - `validate.py` は `csv.DictReader` で `rank`, `id`, `origin` しか読まないので、壊れない。
- ガイドの `energy_per_mol_eV` の説明と `input/csp.toml` の `relax_steps` のコメントから、「GFN2-xTB」という決め打ちをなくす。
- 「エネルギーの絶対値は方法ごとに基準が違い、比べてよいのは同じ方法の中だけ」という注意を、ガイドに書く。

### 5.6 時間予算
- 既存の時間予算の仕組み（ラウンド単位の見積もり）の考え方は変えない。
- **プールを作ったら、最初のラウンドの前に準備ジョブを `n_procs` 個流して、全ワーカーを起動し、モデルを読み込ませる。**
  - ProcessPoolExecutor はジョブが来たときに初めてワーカーを起動するので、プールを作るだけでは読み込みが起きない。
  - 準備の時間は経過時間には数える（予算から引く）。ただし、ラウンドあたりの時間の見積もり（`longest`）には入れない。
  - 準備の時間は `run.log` に書く。
- 途中でプールを作り直したときも、5.3 節のヘルパーで準備ジョブを流す。作り直しによる読み込みの時間も `longest` に入れない。
- xTB でも同じ準備ジョブを流す（中身は計算器を作るだけで、ほぼ一瞬）。方法ごとに経路を分けない【Claude の判断】。
- 時間予算が準備だけで尽きた場合でも、既存の決まりどおり、最初のラウンドは必ず流す。
- `relax_steps`（既定 60）と `relax_fmax`（既定 0.05）は、方法によらず共通とする。
- LJ による事前のふるい（`n_prescreen_keep`）は、方法によらず共通とする。

## 6. 組み込み後に計測すること（結果でガイドの勧めや次の変更を決める）

1. 本パイプラインの条件で、xTB と OrbMol-v2 がそれぞれ 1 時間に何候補を緩和できるか。
   - `n_procs` は 4 と 8 の両方を試す。
   - 8 ワーカー時のピークのメモリ使用量と、ワーカーの同時起動（Warp のカーネルキャッシュ `~/Library/Caches/warp` などの競合を含む）で問題が出ないかも見る。
   - 対象はナフタレンと Se を含む分子。
2. 本パイプラインが生成した候補（詰まった候補を含む）を OrbMol-v2 で緩和したときの、`rejected_deformed` と `failed` の割合。xTB と比べる。
3. 既定の `relax_steps = 60` で打ち切ったときにも、順位（実験構造が上位に来るか、xTB との順位相関）が 300 ステップのときと大きく変わらないか。
4. 1〜3 の結果から、次を決める。
   - ガイドで OrbMol-v2 を勧めるか
   - 2段構成が必要か

これらは使い捨ての試験として行う。結果はガイド（`csp_guide.rst`）の「計算方法の選び方」と「時間の目安」に反映する。

## 7. 後回しにしたもの

- **UMA（uma-s-1.1、task `omc`）**: 文献上は分子結晶で最も実績がある。ただし次の制約がある。
  - OMC25 に Se がない。
  - Hugging Face で利用申請が要る。
  - FAIR Chemistry License（商用可、利用規約あり）である。
  - MPS に非対応で、CPU では遅い。

  利用者が利用申請を済ませたら、2 節と同じ比較試験をし、良ければ 5.3 節の形で選択肢を1つ足す。
- **AIMNet2**: 2 節の試験で、結晶の順位付けに使えないと判断した。
- **orb-v3-conservative-omol**: OrbMol-v2 とほぼ同じ結果だったので、選択肢を増やさない。
- **重みの事前取得だけをする CLI オプション**（`--prepare` など）: 今回はガイドに 1 行のコマンドを書くことで代える【Claude の判断】。

## 8. 実装する人に任せること

- ワーカー内キャッシュの具体的な形と、準備ジョブの実装。
- `relax_many` にプールを渡す引数の形。
- 動作確認に使う小さな構造の細部。
- テストの組み方。ただし次の条件を満たすこと。
  - 重いモデルを読み込むテストは `slow` 印を付け、`orb-models` が入っていない環境ではスキップする。
  - プールの使い回し、準備ジョブ、spawn、`RelaxBackendError` の 1 行エラー、`relax_method` の設定・CLI・CSV 列は、`EMT` 系か偽の計算器で、通常のテストとして確かめる。
  - CI の通常テストは今と同じ時間で終わる。
- ドキュメント（`csp_guide.rst` の日英、README、インストール手順、CLI リファレンス、`input/csp.toml` のコメント）の書き方。5.4 節と 5.5 節の内容は必ず含める。
